# Подсистема безопасности AccessEvent
 
## 1. Роли и права
 
| Роль | Права |
|---|---|
| guest | Просмотр списка мероприятий |
| user | + регистрация на мероприятия, чат, отзывы, личный кабинет |
| organizer | + создание мероприятий, подтверждение заявок, отмена своих |
| admin | + управление всеми мероприятиями и пользователями |
 
Наследование ролей: guest -> user -> organizer -> admin.
 
## 2. Аутентификация: JWT-поток
1. POST /api/register: пароль хешируется, создаётся запись в users.
2. POST /api/login: сервер проверяет хеш и выпускает JWT
   (подпись HS256, срок действия 24 часа).
3. Клиент хранит токен в localStorage и передаёт заголовком
   Authorization: Bearer <токен>.
4. Декоратор token_required проверяет подпись и срок.
5. Декоратор role_required проверяет роль пользователя.
6. Просроченный или неверный токен -> 401; нет прав -> 403.
 
## 3. Хранение паролей
Пароли не хранятся в открытом виде: generate_password_hash из Werkzeug
(PBKDF2 с солью). Это хеширование, а не шифрование: обратной функции нет,
восстановить пароль из хеша нельзя.
 
## 4. Защита от атак
- SQL-инъекции: SQLAlchemy подставляет параметры безопасно,
  строки SQL не склеиваются с пользовательским вводом.
- XSS: Jinja2 экранирует вывод; отключать экранирование (|safe) запрещено.
- Подделка запросов: роль проверяется на сервере, а не только в интерфейсе.
 
## 5. Инклюзивные аспекты безопасности
- Цветовая индикация статусов (pending=жёлтый, confirmed=зелёный,
  cancelled=красный) всегда дополняется текстовым статусом:
  цвет не единственный признак состояния.
- Поле is_deaf в профиле; уведомления отображаются визуально.
 
## 6. Секреты
SECRET_KEY и пароль БД хранятся в .env; файл добавлен в .gitignore
и не попадает в репозиторий.
